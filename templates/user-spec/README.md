# {{项目名}} user spec

这个目录记录**作者对 {{项目名}} 的预期**——{{项目名}} 的 user spec 就是作者的意志。它是整个项目的源头：技术文档、代码、测试都是为了满足这里的预期而存在的派生物。作者亲手写的东西（稿子、笔记、数据）不是派生物，是作者的，不能被覆盖。

**根目录的 [AGENTS.md](../AGENTS.md) 也属于 user spec**：它是作者对工作方式、对 agent 怎么参与的预期，只是位置不在本目录——放在根目录，agent 工具开工时会自动读到。只看 user spec 重建项目时，范围是本目录加上 AGENTS.md（讨论稿除外，见下面「讨论」）。

## user spec 怎么长

- user spec 是一套**维护**方案：可以在项目刚开始时把地基打好，但不是用来凭空造出一个房子的。
- **它的容量和作者的想法成正比。** 刚开始作者没多少想法，user spec 就很小；作者说得越多，它越大。
- **agent 绝不会凭空在 user spec 下创造预期**：不为了填满去问作者问题，不预先摆章节、提纲或问题清单。内容必须有作者表达或认可的依据；表达和组织由 agent 负责。
- 判断一句话该不该进 user spec：作者在意吗？能拿来指导做法或评审吗？作者重读时认得出自己吗？

## 两层内容

### 1. spec 文档（本目录下除 `decisions/`、`discussions/` 以外的文档）

- 用正常文档的形式叙述**作者的预期**：要什么、什么重要、什么不要。
- 以高层次的预期为主。作者通常关心「要达到什么」，而不关心「具体怎么做」。
- 可以提及具体做法——有时具体做法确实重要——但提及时**必须附上对应的决策**（写成「……（见 D-0001）」，D-0001 链接到那条决策的文件），表明这是基于决策的方案，**不与作者预期处于同一层次**。
- 按主题分文件。第一份叫 `overview.md`（总览）；作者的想法多到一份放不下、或者明显是另一个话题时，再新建一份，并在下面的「目录」里加一行。
- 用 `concepts/` 里定下的名字。概念也是 spec 文档，是项目的词典：作者给项目里的东西起的名字记在那里，规则见 [concepts/README.md](concepts/README.md)。

**读法**：spec 文档中未引用决策的叙述 = 作者的预期 = 承重墙。要改动它，等于作者推翻自己，必须先与作者讨论。

### 2. 决策（`decisions/`）

- 一条决策连接**作者的预期**与**具体的做法**：记录当时为什么这样做、经过了怎样的思考、考虑过哪些方案、为什么没有采用。
- 「不用 xxx」同样是决策。
- 决策**可以被推翻**，而且**在符合作者预期的前提下，我们鼓励推翻**：有更合理的方案，或环境发生重大变化时，就选择另一种做法——推翻的方式是写一条新决策取代旧决策，而不是删除。
- 决策不要求作者看过。它的价值是**记录与溯源**：将来想了解历史或推翻时，能知道哪些是作者的预期，哪些是当时思考出来的方案。
- 写法与模板见 [decisions/README.md](decisions/README.md)。

## 讨论（`discussions/`）

讨论复杂、作者需要一份能反复看的讲解、例子或方案比较时，agent 写一份讨论稿，放在 `discussions/`。写法见 [discussions/README.md](discussions/README.md)。

- spec 文档和技术文档是**活的**，要和现在一致；决策和讨论稿是**记录**，写下那一刻的事，之后不再维护，也不删。
- **读法**：讨论稿里写的既不是作者的预期，也不是定下来的方案，可能有讲错、后来又改了的地方。作者的预期以 spec 为准，定下来的以决策为准；讨论稿只说明当时是怎么想的。
- 不管写没写讨论稿，讨论的结论都照常进决策、spec、技术文档。讨论中定下的、以后要做的事，也在 [TODO.md](../TODO.md) 挂一条，指回讨论稿。

## 怎么记

- **主动整理成文档是 agent 的职责**：默认用正常语言转述，合并重复表达，把多轮对话中的同一主题组织在一起，展开「这个」「按刚才说的」等指代。新增想法融入已有内容，使文档连贯、脱离原会话也能读懂。
- **整理的边界是含义**：保留作者要什么、为什么在意、明确不要什么，以及适用范围、条件、例外、要求强弱和确定程度。结合上下文意思明确即可整理，不要求作者像写合同一样表达。不得新增理由、替作者取舍或在不同解释中擅自选一种；实际工作需要解决时再讨论。
- **原话按价值保留**：措辞本身承载重要态度、比喻或个人表达，作者要求保留，或转述容易把尚未明确的想法定死时，保留原话，并融入主题叙述。例如「先做到这个就行」通常应展开为「当前先支持浏览、点击、填写和读取内容即可」（须有上下文依据），不能写成永久性的「产品只支持这些能力」。
- **一次性的东西不进 spec**：一次性的工作指令、确认过程、整理材料的经过不是作者的预期，不因为作者说过就写进 spec。重要的讨论过程写进相关决策的「背景」。
- **正文按主题记录当前预期**：日期和来源标在有用的位置，例如一组预期的出处或一次立场变化，不要求每句话重复标注。核验的是含义的依据，不是与聊天原句逐句对应。
- 作者说正在想、还没想清楚的，写在对应文档的「未定」一节。「未定」只记作者自己说还没想好的；agent 想到的问题在对话里问作者，不起草进「未定」。
- 忠实转述是正文，不标成「agent 注」。agent 额外提出的解释、推断或联想，以「agent 注：」开头，与作者的预期分开。
- 标题、目录、链接这类结构文字由 agent 写，不算 user spec 的内容。

## 一条内容放哪

| 内容 | 放哪 |
|---|---|
| 作者说的想法、要求（「要做到……」「不要……」「……最重要」「……就行」） | spec 文档 |
| 作者亲自规定的细节（具体的数字、工具、步骤） | 决策，决策者「作者」；背后的考量写进 spec。作者没说原因，就写「作者没说原因」 |
| 作者的宏观想法，本身不产生要做的事 | [vision.md](vision.md) |
| 作者说还没想清楚的 | 对应 spec 文档的「未定」一节（只记作者自己说的） |
| 作者说以后要做的（「以后要……」「下一步……」「先不做，之后再……」） | 对应 spec 文档写要什么，保留时间限定；再在 [TODO.md](../TODO.md) 挂一条，链接到详情 |
| 决策定了、还没实现的 | 决策状态写「有效（未实现）」；在 [TODO.md](../TODO.md) 挂一条 |
| 作者给项目里的东西起的名字 | [concepts/](concepts/README.md) |
| agent 为满足预期选的做法，包括「不用 X」 | 决策，决策者「agent」 |
| 修了一个 bug | 新的决策，写「修复的 bug」一节 |
| 发现了还没修的毛病 | 受影响那部分技术文档的「已知问题」一节（见 [docs/README.md](../docs/README.md)） |
| 讨论复杂时写给作者反复看的讲解、例子、方案比较 | [discussions/](discussions/README.md)，是记录；结论照常进 spec、决策 |
| 项目以外的事实（产品、项目、论文、数据集、人物、作品、网站能查到什么、实测到的外部行为），作者给的外部材料 | `references/<名字>.md`，带出处 |
| 对外部东西的看法 | `references/<名字>-thoughts.md`，只记作者说的或明确认可的 |
| 怎么实现的、怎么用 | `docs/` |
| agent 额外提出的解释、推断或联想 | 写在相关内容旁边，以「agent 注：」开头（资料里标「推断」）；忠实转述属于正文 |

作者把项目分成几个相对独立的部分来想时，每个部分可以有自己的 `user-spec/`（含 `decisions/`、`discussions/`；决策编号用自己的前缀，例如 `WEB-0001`）、`docs/`、`references/`、`TODO.md`；全局的决策用 `D-NNNN`。根目录的 TODO.md 只放全局的条目，并列出各部分 TODO 的链接。

## 引用关系

```
spec 文档（作者的预期）
   ↑ 服务于
决策（为什么这样做）
   ↑ 引用
技术文档 / 代码注释 / 其他产出（怎么做的）
```

- spec 文档提及做法时引用决策；
- 技术文档、代码注释等**一切文档**都可以引用决策作为依据；
- 决策可以引用上游决策。推翻上游决策时，沿引用链检查下游决策是否需要一并重新考虑。
- 决策和讨论稿互相指：讨论稿写结论去了哪，决策写讨论见哪。
- 目标：user spec 像 user spec，技术文档像技术文档，二者通过决策良好地连接。

## 变更规则

| 变更 | 谁可以做 |
|---|---|
| spec 文档：新增预期、改变已有预期的含义 | 必须由作者提出或确认 |
| spec 文档：纯整理（不改含义的措辞调整、合并重复、补引用、更新状态） | agent 可以自行完成 |
| spec 文档：「未定」一节 | 只记作者自己说还没想好的；agent 不起草 |
| 概念：新增、改变含义 | 必须由作者提出（见 [concepts/README.md](concepts/README.md)） |
| 决策：新增 | agent 可以自行记录（凡是基于作者需求做出的决定都记下来） |
| 决策：推翻（换了方案、方向反转） | 写新决策取代旧决策，并标注旧决策状态；若取代会改变 spec 文档中的叙述，按 spec 规则处理 |
| 决策：小的修改，或修改刚定下的决策 | 原位修改；有非平凡理由时在决策末尾写「修订记录」 |
| 讨论稿：新建、讨论进行中修改 | agent 可以自行完成；结束后只补「结论去了哪」，内容不再改 |
| TODO.md：挂条目、删掉做完的、整理 | agent 可以自行完成；条目只来自作者说的或已有的决策，每条带链接 |

agent 发现 spec 与需求或现状冲突时，正确的反应不是覆盖，而是停下来问：**「是我理解错了，还是你改主意了？」**

### 作者亲自规定的细节

作者通常不关心细节。如果作者亲自规定了某个细节，背后很可能有更高层次的考量：

- 细节本身记为决策，**决策者 = 作者**；
- 背后的高层次考量写进 spec 文档（不清楚时可以问），并让该决策引用它。

这样将来推翻这个细节时，能知道它当初是为了满足什么。

## 给 agent：遇到「重构」「重做」类需求时

1. 先读 spec 文档，确认哪些是作者的预期（不能变）；
2. 再读相关决策，了解现有做法服务于哪些预期、当时排除了哪些方案、什么条件下应重新考虑；
3. 在满足作者预期的前提下，决策层的一切都可以重新选择——可以并且应该提出结构性优化的建议；
4. 推翻决策时写新决策，说明取代了哪条、为什么。
