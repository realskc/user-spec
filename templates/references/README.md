# 参考：外部资料

这里记录 {{项目名}} 以外、值得留下来的东西：产品、开源项目、论文、工具，也包括**领域资料**——人物、作品、版本、数据集、某个网站或平台能查到什么，以及其他任何值得参考的东西。工作中搜集到的、值得记录的资料都放进来。

**为什么要记**：换 agent 的时候不用重新查资料，资料还可以越积越多、越来越有用。所以 references 里不能有没标注的错误——错误越积越多，就不一定是正效果了。

**什么时候记**：随查随记。为了做事去查的外部事实也算，不要只留在对话或试验记录里；以后可能还用得上的就记；拿不准值不值得记时也记。发现记错了就改。

每个对象（产品、项目、论文、人物、作品、数据集……）一个 Markdown 文件，直接放在本目录下，文件名就是它的名字（例如 `NumPy.md`）。条目多了可以按类别分目录。

- **资料**：文件名就是它的名字；
- **我们的想法**：文件名用 `<名字>-thoughts.md`。还没有想法时可以没有这个文件。

和它密切相关的条目可以各自成文件，用文件名区分；一个对象有多个资料文件时，用 `<名字>-<主题>.md`。

## 资料

- 调研出来的事实：它是什么、怎么做的、有什么限制、实测表现如何……
- agent 可以自行调研、补充、更正，也可以自行新建。
- 只写事实，不写评价；每条注明来源（链接，或「实测」及怎么测的）；文件开头写最近一次核对的日期——外部的东西会变，资料可能过时。
- 不是直接查到、而是推断出来的，标「推断」；没核对过的，标「待核实」（见下面「写法约定」）；来源之间有矛盾的，两边都记下来，查清了再写结论。

## 我们的想法

- 对它的看法：有什么值得借鉴、有什么新奇的、能不能为我们所用……
- 和 user spec 一样，**只记作者说的，或者作者明确认可的 agent 的说法**。agent 自己想到的不记；拿不准作者是否认可时，先问。
- 作者认可的 agent 说法，注明「agent 提出，作者认可」。
- 「明确认可」指作者说了「说得好」「有道理」这类表示赞同的话；没有表态不算。
- agent 的补充说明、推测不放进想法文件：写进对应的资料文件，标「推断」。
- 某个想法变成了对 {{项目名}} 的具体预期时，写进对应的 spec 文档，并链接回这里。

## 写法约定

- **开头**：标题下第一条是 `- 最近核对：YYYY-MM-DD`，写的是文件里任何内容最近一次核对的日期。有的小节、条目是别的日期核对的，就在那一节或那一条里注明日期。接着是来源、许可证等。
- **只用两种标注**：
  - 「推断」：agent 推断出来的，或者 agent 的看法；
  - 「待核实」：还没核实的事实，包括听来的「常见说法」。
  - 不用「未核实」「没验证过」「猜测」这类别的说法。核实了就去掉标注。
- **项目自己要做的事不算「待核实」**：要在哪里测什么、要不要用它，这些是项目的事，写进决策，不写在资料里。
- **「与本项目的关系」**：资料里讲 {{项目名}} 和它有什么关系的那一节叫「与本项目的关系」；项目分成几个部分时，部分的资料里叫「与<部分名>的关系」。这一节只写现状（采用 / 弃用 / 候选 / 不试 / 只作背景……），并链接到对应的决策。项目自己的设计、规则、计划写在决策里，资料里不重复，只链接过去。
- **「作者」只指本项目的作者**：第三方的作者写「原作者」「论文作者」「开发者」或者直接写名字；外部文档里的 user 这类说法，照原意译成「用户」等，必要时注上原文。
- **不记个人机器上的状态**：作者电脑上的路径、临时目录、某个文件在哪台机器上，这些会变、换个地方就没意义，不写。试验本身（跑了什么、在什么上跑、结果、耗时、作者的感受）是领域事实，照记。
- **资料和想法互相链接**：有想法文件的，资料文件开头写一条 `- 我们的想法：[<名字>-thoughts.md](<名字>-thoughts.md)`；想法文件标题下写 `资料见 [<名字>](<名字>.md)。`。
